Design note mock · /admin/data-sources

Sources in two bands, collections as a lens of their own

Third version, reworked after five independent review passes (information architecture, admin-persona walkthrough, design-system consistency, simplicity, Library coherence). Numbers are illustrative of one production instance: 8 SharePoint connections, 1 Keboola project, ~390 collections, ~250k files.

Kept (agreed by 4–5 of 5)

  • Rewrite the lede — it names only table sources today.
  • Sort table sources first. The table card is last only because of ORDER BY name.
  • Bands "Table sources / File sources", only when both kinds exist; hint = one clause, no links.
  • A Collections lens — the data view Access lacks: source, file state, facts.

Changed since v2

  • The strip keeps its arrows. The new lens goes past the break, like Semantic sources.
  • "Files" → "Collections". The Library section is Artefacts; Access, wizard and card say Collections.
  • "Document sources" → "File sources". Collides with Semantic sources' own gloss.
  • The amber badge is a link. Today it is a plain span.
  • "Who can see it" lives in Access. The lens shows a chip and opens the existing Share dialog.

Dropped

  • Single-file view — the collection's Library page already has status chips and Re-ingest.
  • Picker grouping — a group of one is a label.
  • "Scope" outside the wizard — means audience one tab away.
  • Ontology link from a hint — the page has no nav home to paper over.

Collection → its Library page (files, status, Re-ingest). Needs attention → the same page filtered to needs_review + rejected. Share… → the existing share dialog; the full grant audit stays in Access. The Facts column is absent on a DuckDB-backed instance.
·
Why a lens when Access already lists collections. Access answers "who sees what" across everything — without source, file state or facts. This is a data question: what came from which source and in what state. One row per collection, one band per source.
·
No new "Grant". Share… opens the dialog the Library detail already has. Access built the one picker; a fourth writer of collection grants would drift.
·
Vocabulary. Table ↔ file (the unit), data package ↔ collection (the grant container). A collection is to documents what a data package is to tables — hence its place right after it. "Folder" and "scope" are not said here.
·
When the tab shows. Only on an instance with a file source or at least one collection (when: in admin_nav.py) — the same rule as "bands only when both kinds exist".
·
Endpoint first, page second. Count-first (count_by_corpus + one grouped status count), and the source card reads the same query — the lens becomes the fix for today's page cost, not an addition to it.

D · Found beside the question

these decide whether the result is usable at this size
The Sources page is O(files). The SharePoint card's cell decodes every file of every scope on every render and after every mutation (_sharepoint_pipeline_cell). The lens must be count-first and the card must read the same query.
Access may not load on such an instance. It eagerly projects corpus_file too: ~390 collections × all their files into one JSON. Verify before linking anything there.
Dead link in Access: "Open" on a collection targets /library/d/{id}; the route is /library/{slug}. Ten minutes.
Seven "Private Equity n/6" cards are one site split for crawl parallelism; a root-scope connection is the goal. Bands do not shrink seven cards. Do not design around a workaround.
The one decision: is a collection the document world's data package — a grant container in the same Data section (this mock) — or are documents a second product line with their own section Documents: Sources → Collections → Ontology & graph? The reviews lean to one section now, and to the split once a second document connector exists — which would also give Ontology the nav home it lacks.
