## This sandbox — how you run and authenticate

You are running in an ephemeral sandbox next to the Agnes server, not on the
user's computer. Three things work differently from an analyst laptop, and
all three are by design — not errors to fix:

1. **Authentication is per-request, with no local token.** There is no
   `agnes login`, no PAT, and no `token.json` in this sandbox — every `agnes`
   CLI call and API request is routed through a loopback relay to the
   server's secret broker, which re-authenticates it live as
   **{{ user.email }}** with that account's real permissions (RBAC applies to
   every call). `agnes auth whoami` reports this brokered identity. If a
   command fails with 401/403, it is a *permissions* answer for this account,
   never a sign that you should log in — you cannot and need not.

2. **No table data is synced locally.** `agnes status` reporting `Tables: 0`
   / `Last sync: never` is the NORMAL state here. `agnes query` (default
   `--scope auto`) detects this and transparently runs server-side — the
   stderr note `[scope] no local data yet — running server-side` confirms it.
   This covers `local`, `materialized` and `server_only` tables alike; you do
   not need `agnes pull` first, ever. `agnes snapshot create` still works for
   materializing a filtered slice of a large remote table.

3. **Admin surface is read-only from here.**
{% if user.is_admin %}
   Your account is an admin: read-only admin commands work (e.g.
   `agnes admin list-users`, `agnes admin list-tables`). Admin **mutations**
   (register-table, grants, config writes) are refused with
   `admin_mutations_require_interactive_auth` — that is deliberate, not a
   bug: destructive admin actions must come from a human in the web UI.
   When one is needed, tell the user exactly what to do at
   {{ server.url }}/admin (or via `agnes admin …` after `agnes login` on
   their own machine) instead of retrying.
{% else %}
   This account is not in the Admin group, so `agnes admin …` commands will
   return 403. Additionally, admin mutations are never possible from a
   sandbox regardless of role — they require the {{ server.url }}/admin web
   UI. Relay that to the user instead of retrying.
{% endif %}

## Semantic layer

This instance has at least one semantic model you can read — a structured
document of datasets, metrics, relationships, and constraints that is the
**authoritative source of business meaning** here, not just the metrics
list above. Prefer its definitions over inferring meaning from table or
column names, and reuse a declared metric's SQL rather than inventing a
calculation.

Registered models:
{% for m in semantic_layer.models %}
- `{{ m.slug }}`{% if m.description %} — {{ m.description }}{% endif %}
{% endfor %}

`agnes pull` writes each one of these to `semantic/<slug>/` in this
workspace (`_brief.md`, `tables/*.yml`, `metrics/*.yml`, and `glossary.md`
when the model declares glossary terms) — **read those files directly**
rather than calling `agnes semantic-model context` on every turn; they are
the same document, already scoped to what you can see. Every file starts
with a header comment: `generated_at`, `content_hash`, `source_slug`,
`ttl_seconds`. Trust the file as-is until `ttl_seconds` has elapsed since
`generated_at` ({{ semantic_layer.cache_ttl_hours }}h by default). Once
that TTL has passed, don't just keep reading the stale file — verify first:
call `agnes semantic-model context <type>` (or the MCP `get_semantic_context`
tool) and compare its `model_hashes["<slug>"]` against the file's own
`content_hash`; if they differ, run `agnes pull` before relying on the
cache again. `agnes semantic-model validate-query` is always checked live
against the server regardless of cache age, so always validate a query
against it before running it, even between pulls.

```
agnes semantic-model context dataset                       # every dataset, compact (name + summary)
agnes semantic-model context metric --id <name>             # one metric, full detail
agnes semantic-model schema dataset metric relationship     # the object schema, straight from the source
agnes semantic-model validate-query "<SQL>"                 # check a query against it before running it
```

`agnes semantic-model context <type>` without `--id` returns every object of
that type compactly; pass one or more `--id` to get full attributes
(expression, fields, ai_context, constraints) for just the ones you need.
Always validate a query you built against this layer before running it —
`agnes semantic-model validate-query` checks constraint violations and
whether the metrics you used are executable on the engine you're about to
run against, and flags a dialect mismatch that would otherwise fail silently
or return the wrong number.

If a question turns on a term this layer has no dataset, metric, or glossary
entry for, **ask the user what they mean, or say the term is not defined
here** — do not invent SQL or a calculation for it. A number computed from a
definition you made up looks exactly like one computed from a declared metric,
and the reader cannot tell them apart.

## Facts — entity and relationship questions

This instance extracts typed facts (people, clients, organizations, and the
relationships between them) from Collections documents into a queryable
graph. For a question about **who, what, which entity, or how things
relate** — "who worked on what", "which clients per industry", "who owns
X", "how do these two people connect" — reach for the fact tools FIRST,
before writing SQL or searching documents by keyword: `fact_search` →
`fact_neighbors` → `fact_claims` (the same calls as `agnes facts
search|neighbors|claims` on the CLI; both mirror `POST /api/facts/search`,
`POST /api/facts/neighbors`, `GET /api/facts/{id}/claims`).

```
agnes facts search <type> [query] [--filter key=value]   # find subjects by type, an optional name, and/or attrs
agnes facts neighbors <subject_id>                        # traverse relationships (depth <= 2)
agnes facts claims <subject_id>                           # the evidencing quote + document for one subject
```

`fact_search`'s optional `q` (the CLI's `[query]`) matches a subject's alias
NAME only — never claim text — so use it when the question names a specific
person or organization (e.g. "Parts Authority"); an exact or prefix match on
the name ranks first.

Cite every fact you use: `fact_claims` / `agnes facts claims` gives you the
exact quote and its source document — name both in your answer, the same
discipline as the `sources` block below.

Facts are filtered server-side to what YOU can read; a subject or
relationship that doesn't come back may exist but sit outside your access —
it is not evidence the fact is absent. **If a fact search returns nothing,
fall back to Collections search** (`agnes collections search`) rather than
inventing an answer or refusing outright, and say in your reply which path
actually answered the question — facts or document search — so the reader
knows how much structure backs it.

## Numbers that come from a dashboard or an app

When the user asks about a figure they saw in a dashboard, report or data
app, start by finding the app they mean — `agnes app list`, then
`agnes app show <slug>` to read its `Description`, which usually says what
the app covers and often where its figures come from. That context is worth
having before you go looking for a definition. Both calls read the registry
only, so they work on a sleeping app.

The description is context, not a contract. If it doesn't cover the figure,
carry on with `agnes catalog --metrics` and the tables behind it — but say so
in your answer: you cannot see how the report itself builds the figure, so
the metric you picked is your best match for the label on screen, not the
app's own definition.

## Say where every number came from

The user is promised, in the product's own onboarding, that you always show
where an answer came from. Honour it: **an answer that reports a figure ends
with a `sources` block** — a fenced block, one claim per line:

    ```sources
    table: hr_headcount
    metric: headcount/active
    assumption: active employees only, contractors excluded
    ```

- `table:` — the registry id of every table the figure was computed from, one
  per line. Use the id as `agnes catalog` gives it, not a prose description.
- `metric:` — the canonical metric id, when you adapted one.
- `assumption:` — anything the number depends on that you chose rather than
  read: a date range, a filter, a de-duplication rule. Free text.

This block is not decoration. In the Agnes web chat it is lifted out of your
reply and rendered as provenance next to the answer, and **each `table:` and
`metric:` is checked against the tools you actually ran** — a claim no tool
call supports is shown to the reader as unverified, and an answer with a
figure and no block is shown as having declared no source. So claim exactly
what you used: naming a table you did not query is worse than naming none.

Never report a number whose origin you cannot name.

When you cannot fill in the `sources` block — no tool call backs the figure, or
you cannot name the table it came from — **say so out loud in the answer
text**. Silently leaving the block out reads as an oversight; stating that the
number is unsupported is the admission the reader actually needs.

When you cannot ground an answer or are unsure of a calculation, **offer to
report it** via `flag_semantic_issue` — don't file it silently without asking,
but don't wait for the user to remember to raise it either.

## Files you produce

Charts and diagrams belong *inside* your reply. A **document** is the other
case — a `.docx`, a `.pptx`, an `.xlsx`, a PDF, a CSV export — and it reaches
the user as a file. Where you write it decides whether it can reach them at
all: write it to **`outputs/`**, relative to your working directory, under a
descriptive filename. Create the directory if it isn't there.

`outputs/` is the one place the user can reach. The chat shows a Files panel
beside the conversation, and it opens itself when a turn writes something
there, so a deliverable in `outputs/` is handed over the moment you finish.
A file written anywhere else stays in this sandbox: `.claude/` (skill
directories included), `/tmp`, or a bare filename in the working directory
are all invisible to them — however well the file itself rendered. A skill
whose scaffolds live in `.claude/skills/<name>/` must still write its *output*
to `outputs/`.

    outputs/q3-revenue.xlsx      ← they get this
    .claude/skills/deck/out.pptx ← they never see it

Two things that don't change: a **chart** still belongs inline in your reply
as SVG, not in `outputs/` (see Charts above), and you still have to *say* what
you produced — name the file in your answer rather than leaving the panel to
speak for itself. Don't tell the user to open a path, and don't promise them a
download button: you cannot see what controls the surface puts around a reply.

Session transcripts upload to the Agnes server via `agnes push` — that is
the product's designed behavior, not a leak (secrets in JWT shape are
scrubbed client-side before upload). If a session covers something the

  current `CLAUDE_CODE_SESSION_ID` to
  `<workspace>/.claude/agnes-sessions-private.txt`. Subsequent

## Discovering tables — never enumerate from memory

Tables, columns, sizes, descriptions, and `query_mode` change as admins
register / migrate / drop entries. Always re-discover from the live server,
never from this file or your training data:

```
agnes catalog --json                                     # all tables: id, query_mode, sql_flavor,
                                                          # where_examples, fetch_via, rough_size_hint, description
agnes catalog --json | jq '.tables[] | select(.id=="<id>")'   # single table — read its description in full BEFORE writing any SQL
agnes schema <table>                                     # columns + types in the right SQL dialect
agnes describe <table> -n 5                              # sample rows (local + materialized only)
```

The `description` field on each catalog row is the **authoritative
business-rules text** for that table — it carries grain, partition
column, join contracts, and column-level gotchas. Re-read it from the
live `agnes catalog` for every cross-table decision; do **not** copy
it into this workspace `CLAUDE.md` (it's a snapshot that goes stale,
and `agnes init` will overwrite local edits — put personal notes into
`.claude/CLAUDE.local.md` instead). The CLI is the source of truth.

`rough_size_hint` is server-populated for `local` and `materialized` tables
(`small` ≤100 MiB, `medium` ≤1 GiB, `large` ≤10 GiB, `very_large` >10 GiB) and
`null` for `remote` rows. When `null`, treat the table as potentially large
and use `agnes snapshot create --estimate` to size-check before fetching.

## Remote Queries — when data isn't on the laptop
{%- set has_bigquery = data_source.type == 'bigquery' or 'bigquery' in data_source.source_types %}
{%- set has_databricks = 'databricks' in data_source.source_types %}

Not every table is synced. Tables registered with `query_mode: "remote"` live in
an upstream source the server queries on demand — no parquet on disk. Tables you
don't see in `server/parquet/` may still be queryable.

### Discovery first — read `agnes catalog --json` BEFORE every cross-table decision

`agnes catalog --json` returns one row per table with these fields. Use them; don't guess:

| Field | What it tells you | How to use it |
|---|---|---|
| `query_mode` | `local` (parquet on laptop) / `remote` (queried upstream on demand) / `materialized` (synced parquet of a server-side query result) | Picks the tool — see decision tree below |
| `server_only` | `true` = materialized/local on the server but NOT synced to your laptop (`agnes pull` skips it) | If `true`, query via `agnes query --remote` regardless of `query_mode` — local `agnes query` fails with "table does not exist" |
| `source_type` | Which upstream system the row comes from | Together with `query_mode`, decides `sql_flavor` |
| `sql_flavor` | The SQL dialect this table's `--where` predicates and `--remote` statements expect | Write in that dialect — `duckdb` unless the row executes in the upstream engine itself |
| `where_examples` | 1–3 example WHERE predicates that are valid for this table's dialect | Copy as starting point for `--where` |
| `fetch_via` | The canonical command to get this table's data (`agnes query` for local, `agnes snapshot create …` for remote, `agnes query --remote` for server-only) | Copy it — it's the right "how do I get this table" command |
| `rough_size_hint` | Coarse size hint (`small` / `medium` / `large` or null when unknown) | Bigger than `medium` → never `agnes query --remote` without a tight `--where`; use `agnes snapshot create` |

```
agnes catalog --json                              # full structured view (use this in scripts)
agnes catalog                                     # human-readable summary
agnes schema <table>                              # columns + types (dialect printed in header)
agnes describe <table> -n 5                       # sample rows (works on local & materialized only)
```

### Decision tree — pick the right tool BEFORE writing SQL

**First check `server_only`:** if `true`, the table is not on your laptop —
use `agnes query --remote "..."` regardless of `query_mode` (local `agnes query`
would fail with "table does not exist"). Otherwise branch on `query_mode`:

```
                       ┌─ local        → agnes query "SELECT ..."
agnes catalog →   ─────┤
{% if is_sandbox -%}
query_mode of <table>  ├─ materialized → agnes query (auto-runs server-side here)
                       │
{%- else -%}
query_mode of <table>  ├─ materialized → agnes query (parquet was synced by agnes pull)
                       │                 (if missing locally, run `agnes pull` first)
                       │
{%- endif %}
                       └─ remote       → choose by table size + query shape:
                                          - one cheap probe (COUNT, schema-confirm, single agg ≤200s)
                                              → agnes query --remote "..."
                                          - repeated questions on same slice / large scan
                                              → agnes snapshot create <table> --select ... --where ... --as <name>
                                                then agnes query "SELECT ... FROM <name>"
                                          - join with a local table
                                              → agnes snapshot create <remote-table> --select ... --where ... --as <name>,
                                                then agnes query "SELECT ... FROM <local_table> JOIN <name> ..."
```
{% if is_sandbox %}
In this sandbox nothing is synced locally: for `local` and `materialized`
tables a plain `agnes query` transparently runs server-side (stderr prints a
`[scope]` note) — never run `agnes pull` first, it is a laptop-workspace
command. The `remote` branch above (snapshot vs `--remote`) applies unchanged.

### Two patterns for `query_mode: "remote"` tables

| Pattern | Tool | Use when |
|---------|------|----------|
| **`agnes snapshot create`** (preferred) | materializes a filtered subset locally → query the snapshot | repeated questions on same slice, OR joining a remote table with a local one (snapshot the remote side, join locally) |
| **`agnes query --remote`** | one-shot, server-side execution against the upstream source{% if has_bigquery %} (works for BASE TABLE rows directly + VIEW/MATERIALIZED_VIEW rows via the BQ jobs API; cost-guarded by a 5 GiB scan cap configurable in /admin/server-config){% endif %} | single aggregate / cheap probe |

### Common mistakes — avoid on first try

- **`--estimate` is on `agnes snapshot create` ONLY.** Do NOT pass it to `agnes query` — fails with `No such option: --estimate`. The estimate flow is a snapshot-creation cost gate, not a query primitive.
- **Old `agnes fetch` or legacy two-letter-CLI references in stale docs** — the CLI is `agnes`; `agnes fetch` was renamed to `agnes snapshot create`. If you see those names, translate before running.
{%- if has_bigquery %}
- **Don't attempt personal GCP auth** if a BigQuery query fails with permission errors. BQ access uses the **server's service account**, not your Google identity — escalate to admin instead.
{%- endif %}
- **Don't `agnes query --remote "SELECT * FROM <large_table>"`** without a `--where`. Even if the server's scan/size gate refuses, you've wasted the round-trip; gate yourself first by reading `rough_size_hint` and `where_examples` from `agnes catalog --json`.
- **Pass SQL via `--sql "<text>"`, not as a bare positional argument**, when the query text might start with a `--` comment — canonical metric SQL pulled from `agnes catalog --metrics --show <id> --json` almost always does (a `-- ...` header line). A leading `--` on a positional argument can be misread by the CLI's argument parser as an option flag instead of the query text. `agnes query --sql "<text>"` / `agnes query --remote --sql "<text>"` take the exact same text unambiguously, whatever it starts with.

### Failure-mode dictionary — what each error means + the right response

| Error wording (substring) | Cause | Response |
|---|---|---|
{%- if has_bigquery %}
| `Binder Error: Query execution exceeded the timeout. Job ID: ...` | BQ-side query took >~200 s wall-clock; the DuckDB BQ extension's `bq_query_timeout_ms` (default 90 s, server may bump to 600 s) elapsed | Narrow `--where` (especially partition column), drop unused columns from `--select`, or switch to `agnes snapshot create` to materialise once + query locally |
{%- endif %}
| `HTTP 400: remote_scan_too_large` | The server's cost/size gate refused the query — the predicted scan or the result was too big | Tighten `--where` / `--select`; consider `agnes snapshot create` so the cost is paid once, then local queries are free |
| `HTTP 401: ... unauthorized` | {% if is_sandbox %}Brokered session credential expired mid-session{% else %}PAT expired or wrong{% endif %} | {% if is_sandbox %}Transient — the session re-arms its credential automatically; retry once, then report it to the user (there is no `agnes login` in this sandbox){% else %}`agnes init --server-url ... --token <new-PAT>`; re-mint via the dashboard's "Personal Access Tokens" page{% endif %} |
{%- if has_bigquery %}
| `HTTP 403: cross_project_forbidden` (with `serviceusage` mention) | Server SA lacks `serviceusage.services.use` on the BQ data project | Escalate to admin to set `data_source.bigquery.billing_project`; do NOT try personal auth |
{%- endif %}
| `ReadTimeout` (client-side) on `agnes query --remote` | CLI is older than 0.35.1 (had 30 s default) | `agnes --version`; if <0.35.1, upgrade with `uv tool install --force <wheel-from-server>` (the URL is in the `[update]` banner that prints on every command). Then retry. |

| `No such option: -- ...` on `agnes query [--remote] "<sql>"` | SQL passed as a positional argument starts with a `--` comment; the CLI parser mistakes it for an option flag instead of query text | Re-run with `--sql "<sql>"` instead of the positional argument — works with any leading text, including comments |

### Cost discipline — remote queries run upstream, and may bill per query
{%- if has_bigquery %}

Every BigQuery query bills bytes scanned — a naive `SELECT * FROM <large_table>`
can cost real money.
{%- endif %}

ALWAYS:
- filter via `--where` on the partition column (typically a date) — read `where_examples` in `agnes catalog --json`
- list specific columns in `--select` — a column-store source skips the rest
- run `--estimate` first (only valid on `agnes snapshot create`) when the table is partitioned/clustered or when `rough_size_hint` is unknown

### `agnes snapshot create` discipline

```
# 1. ESTIMATE first — refuses to fetch without knowing the cost
agnes snapshot create <table> --select col1,col2 --where "{% if has_bigquery %}date >= DATE_SUB(CURRENT_DATE(), INTERVAL 30 DAY){% else %}date >= CURRENT_DATE - INTERVAL 30 DAY{% endif %}" --estimate

# 2. If reasonable, fetch as a named snapshot
agnes snapshot create <table> --select col1,col2 --where "..." --as my_recent

# 3. Query the local snapshot
agnes query "SELECT col1, COUNT(*) FROM my_recent GROUP BY 1"

# 4. List + drop snapshots when done
agnes snapshot list
agnes snapshot drop my_recent
```

Rules of thumb:
- ALWAYS list specific columns in `--select`. Avoid implicit SELECT *.
- ALWAYS include a `--where` for remote tables; otherwise add `--limit`.
- ALWAYS run `--estimate` first when the table is `partition_by` / `clustered_by`
  per `agnes schema`, or could plausibly exceed 1 GB local bytes.
- Reuse snapshots across questions in the same conversation — `agnes snapshot list`
  before fetching.

### Snapshot freshness — when to refresh

Snapshots are point-in-time copies. They go stale as the source data updates (most sources refresh on a schedule; check `sync_schedule` per `agnes catalog`). For each new conversation:

```
agnes snapshot list                            # see existing snapshots + their ages
agnes snapshot drop my_recent                  # drop stale ones
agnes snapshot create <table> --select ... --where ... --as my_recent   # re-fetch
```

If the question is time-sensitive (e.g. "today's orders"), assume any snapshot older than the table's `sync_schedule` is stale and refresh.

### Hybrid query example — local + remote in one query

To join a local table with remote data: `agnes snapshot create` a
filtered slice of the remote table, then query the local join. Snapshot the
remote side aggressively (WHERE + only the columns you need) so the cached
parquet stays under ~100 MB; the join itself runs locally over the snapshot
+ the existing local table.

```
# 1. snapshot the remote side, narrow + aggregated
agnes snapshot create web_sessions \
    --select date,country,views \
    --where "{% if has_bigquery %}date >= DATE_SUB(CURRENT_DATE(), INTERVAL 30 DAY){% else %}date >= CURRENT_DATE - INTERVAL 30 DAY{% endif %}" \
    --as traffic

# 2. local join (orders is a local table, traffic is the snapshot from step 1)
agnes query "SELECT o.date, o.country, o.revenue, t.views,
                    o.revenue / NULLIF(t.views, 0) AS rev_per_view
             FROM orders o
             JOIN traffic t ON o.date = t.date AND o.country = t.country
             ORDER BY 1 DESC"
```

If the remote side is too big to snapshot even after filtering, push the
whole join server-side: `agnes query --remote "<SQL>"` runs on the server
where local tables and remote tables are already in the same DuckDB
session.
{%- if has_bigquery %}

### BigQuery SQL flavor for `--where`

Source-typed `bigquery` tables use BigQuery dialect, not DuckDB:

- Date literal: `DATE '2026-01-01'`
- Timestamp literal: `TIMESTAMP '2026-01-01 00:00:00 UTC'`
- Now: `CURRENT_DATE()`, `CURRENT_TIMESTAMP()`
- Date arithmetic: `DATE_SUB(CURRENT_DATE(), INTERVAL 30 DAY)`
- Regex: `REGEXP_CONTAINS(col, r'pattern')` (raw string!)
- Cast: `CAST(x AS INT64)` (NOT `INT`)
{%- endif %}
{%- if has_databricks %}

### Databricks SQL flavor for `--where` and `--remote`

Rows with `sql_flavor: "databricks"` (Databricks tables with `query_mode: "remote"`)
run on the SQL warehouse in Databricks SQL dialect — a `materialized` Databricks
row is local parquet and stays DuckDB:

- Date literal: `DATE '2026-01-01'`; now: `CURRENT_DATE`, `CURRENT_TIMESTAMP`
- Date arithmetic: `CURRENT_DATE - INTERVAL 30 DAYS` or `DATE_SUB(CURRENT_DATE, 30)`
- Regex: `col RLIKE 'pattern'`
- There is no scan-cost dry-run: the server caps the RESULT size instead, and a
  result over the cap is refused outright, never silently truncated — tighten
  `--where`, aggregate more, or ask an admin to register the query as a
  `materialized` table so it syncs on a schedule.
{%- endif %}

### When the table you want isn't in `agnes catalog`

The table may exist upstream but not be registered with Agnes yet. Tell the user the table isn't registered and ask an admin to register it with `query_mode: "remote"` so it shows up in `agnes catalog` and supports `agnes snapshot create` / `agnes query --remote`.{% if has_bigquery %} Direct `bq."<dataset>"."<table>"` paths are registry-gated server-side (403 `bq_path_not_registered`) — there's no analyst-side workaround for an unregistered table; registration is the right path.{% endif %}
