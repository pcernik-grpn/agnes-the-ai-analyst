### Fixed
- **On a SharePoint connection whose scopes share one physical drive, the automatic parallel crawl no longer multiplies work instead of dividing it.** The shard planner's "leftover" (remainder) shard is meant to cover loose files and anything created after planning, scoped to whatever the crawled scope itself covers — but for a FOLDER scope it was always built against the whole drive root regardless, and a connection with many folder scopes on one drive got that same drive-wide plan duplicated once per scope. Observed live on a connection with several hundred folder scopes on one drive: the planner produced hundreds of shards whose "remainder" targets all pointed at the entire drive, so each scope's own leftover shard independently re-walked the whole site (18 running children each already past 100k files seen, 21 minutes in, none of ~800 shards done — stopped by hand). A remainder shard now inherits its own scope's root instead of the drive root, unless the scope genuinely is the whole drive; sibling and nested scopes sharing a drive each stay bounded to their own subtree.
- **Opening a large collection's Library page no longer re-scans the whole fact graph to render a 27-row summary.** `GET /library/<collection>` measured 4.5-4.8s server-side on a collection with ~291k files / 801k facts / 730k edges — a `Parallel Seq Scan` of the whole `facts` table hash-joined to `fact_collection_membership` to compute the per-type fact-count breakdown, plus a second leg (the `possible_duplicate_of` review-item candidates) whose `e.src IN (…) OR e.dst IN (…)` compiled as two independent hashed subqueries and could degrade into a scan of nearly the whole `edges` table. The type breakdown now reads a new maintained companion table, `fact_collection_type_counts` (Postgres-only, kept current by the same incremental/rebuild writers as the existing `fact_collection_stats`), for an unrestricted caller only — a caller whose visibility is narrowed by RBAC, audience tiers, or `all_evidence` mode still takes the exact per-caller computation, since a maintained per-collection total cannot express that narrowing. The review-item leg is rewritten as a UNION of two joins so Postgres can build its hash from the (usually tiny) filtered side instead of the full candidate set, twice.

- **Library/knowledge search (`GET /api/knowledge/search`) no longer pays a fixed multi-second tax on every query on a large collection.** Measured on a ~285k-file, ~14.7M-chunk collection: every search took ~10.5s regardless of term frequency, `limit`, or `lexical_only` — the ranking itself was fast (0.2-0.4s), but resolving citation filenames for the filename fallback (`apply_filename_fallback`'s `prepare` pass) `list_for_corpus`-ed every file row of every corpus in scope, an O(files in the collection) cost (~3.7-4.3s) paid on nearly every real query: the pass's own skip condition ("some passage already explains the whole question") rarely holds for an ordinary multi-word query, so this was not a rare edge case. Citation filenames for the (already-bounded) candidate pool are now resolved with a bulk-by-ids repo lookup (`corpus_files_repo().filenames_for_ids`) instead of a whole-corpus listing — O(candidates), independent of collection size. Retrieval quality is unchanged: the filename fallback still triggers on exactly the same condition and returns exactly the same ranking.
- **A SharePoint crawl's bookkeeping table no longer grows tens of gigabytes a day and never gives the space back.** The connection-level state row's `ctags`/`failed_items`/`empty_items` maps grow one entry per crawled file — tens of megabytes combined on a connection with a few hundred thousand documents — and every checkpoint (once per delta page) rewrote that whole row: Postgres always produces a brand-new toasted value for a changed `jsonb` column, even via `jsonb_set` targeting one key, so every checkpoint orphaned the previous copy's TOAST chunks (measured on a running instance: ~21,900 dead TOAST tuples/minute, ~60 GB/day of table growth while a crawl runs — autovacuum reclaims the space for reuse but never returns it to the OS). The three maps now live in a new per-file table (`sharepoint_crawl_items`, one row per file), and a checkpoint flushes only the files that actually changed since the last one; the connection's own state row keeps just the small, genuinely whole-state fields (delta links, the last run report, resync markers). A connection already mid-crawl when this ships is migrated in place, on its very next checkpoint, with no operator action and no lost progress.
- **Shard workers of a parallel SharePoint crawl no longer die with a database deadlock and lose their slice of the work.** With many shard children now genuinely running in parallel, two children whose scopes overlap can legitimately checkpoint the same `sharepoint_crawl_items` row(s) at the same time; each checkpoint applied its batch of upserts in whatever order its own process happened to iterate, and Python's per-process hash randomization made two processes touching the same rows disagree on that order — a classic lock-ordering deadlock (`psycopg.errors.DeadlockDetected` on the `ON CONFLICT` upsert). Observed on a live crawl: 6 of 24 concurrently-running shard jobs failed within two minutes. Row-level writes within one checkpoint are now applied in a single, globally sorted `stable_id` order regardless of which field or which order the caller built its batch in, which removes the lock cycle by construction, plus a small bounded retry for whatever narrow window a third overlapping writer could still hit.
- **A long-running background job no longer pins the database-wide vacuum horizon for its entire runtime.** `seed_lease()`, `rebuild_lease()`, and `knowledge_packaging_lease()` in `src/db_pg.py` each acquire a session-scoped Postgres advisory lock but never committed the connection that took it — under SQLAlchemy 2.x "commit as you go" that left the connection `idle in transaction` for the whole guarded operation, pinning `backend_xmin` and blocking autovacuum ANYWHERE in the database from reclaiming any row version created after the lease was taken, regardless of per-table tuning. Measured on a live instance: a `knowledge-packaging` job held its lease for 6.7 hours idle in transaction while one heavily-updated table's TOAST accumulated 8.9M dead tuples / 52 GB against 2 MB of live heap data, with autovacuum running every ~5 minutes and reclaiming nothing. Each lease now commits immediately after acquiring the lock — the lock itself is session-scoped, not transaction-scoped, so mutual exclusion is unaffected; only the pinned snapshot goes away.
