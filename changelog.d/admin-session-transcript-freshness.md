### Fixed
- **The admin session transcript viewer no longer reads as empty just because the export sweep hasn't ticked yet.** A web-chat session's transcript `.jsonl` is normally (re-)written by a periodic sweep, which lags the session's own activity by up to its scheduler cadence (minutes). Opening `GET /api/admin/sessions/{username}/{session_file}/transcript` (`/admin/sessions/...`, `agnes admin sessions show`) for a session inside that window used to look identical to "this session never had a transcript at all" — the web viewer even rendered the resulting 404 body as an empty, error-free transcript. The transcript route now brings a stale-or-missing chat export current on demand before rendering (the same idempotent write the sweep would perform a few minutes later), and a genuinely unresolvable case now returns a structured 404 that names the reason (no such session, chat-transcript export disabled on this instance, or exported but pending) instead of a bare "not found". The web viewer and `agnes admin sessions show` now surface that reason instead of silently showing "no conversational events".
- **A chat session past 500 messages no longer has its transcript silently cut off.** The export read one page of messages and treated that as the whole conversation, so a long chat's admin transcript quietly ended 500 messages in with a current-looking mtime and no indication anything was missing. The export now pages through the full conversation, oldest to newest.
- **A message that arrives while a transcript is being (re-)exported is no longer lost to the freshness check.** The export used to rely on the file's mtime (set to the moment the write finished) as a proxy for "how current is this transcript", so a message committed between the read and that write was absent from the file yet older than its mtime — indistinguishable from "already current". The freshness check now compares against the newest message the export actually wrote instead, so a transcript that raced a write is correctly reported stale and picked up on the next check.
- **Two overlapping transcript exports for the same session could publish an interleaved or corrupted `.jsonl`.** The periodic sweep, a session teardown hook, and the on-demand transcript viewer can all export the same chat session around the same time with no lock between them; they used to share one fixed temporary file, so a losing writer could interleave into or delete the winner's in-flight write. Every export (and its coverage sidecar) now stages to its own uniquely-named temporary file before atomically replacing the target, so the worst case is "the export that finishes last wins" — never a partial or merged transcript.
- **A corrected re-export of a chat transcript could stay invisible to the usage-rollup pipeline, undercounting that session's token/cost totals.** The pipeline's cheap "already processed" prefilter compares a transcript's file-modification time against when it was last processed; a re-export whose content watermark predated an earlier processing pass could look untouched even though its bytes had just changed, and the rollup was never recomputed. The prefilter now sees every re-export, independent of how old the messages inside it are.
- **A transcript export could silently drop a message that shared its exact timestamp with another message at a page boundary.** Paging through a chat session's messages resumed strictly after a timestamp, so two messages persisted in the same instant (routine under load) could leave one of them permanently unreachable once the page boundary fell between them. Pagination now orders and resumes on the message's timestamp *and* id, so a position inside a tie is always representable.

### Internal
- The periodic chat-session export sweep (`services/session_pipeline/runner.py::_sweep_chat_session_exports`) and the new on-demand check now share one staleness definition (`app/chat/session_export.py::is_chat_export_stale`) instead of two independent mtime comparisons.
