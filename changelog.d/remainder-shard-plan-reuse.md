### Fixed
- **A SharePoint connection's already-persisted shard plan is no longer served back verbatim once it predates the "remainder scoped to the scope's own subtree" fix.** The remainder-scoping fix below only corrected how a plan is *computed*; a connection that had already been planned before it shipped kept its stale, pre-fix plan — folder scopes' remainders still pinned at the whole drive root — because plan reuse only checked whether the scope set had changed, never whether the persisted shape was still trustworthy. Observed live: a 388-folder-scope connection sharing one drive, already planned once before the fix deployed, kept re-enqueueing the same 388 whole-drive-root remainders on every later trigger. A persisted plan is now discarded and rebuilt on the next trigger, same as a scope-set change, when ANY of its shards shows that stale shape — a folder scope's shard pinned at the drive root, whatever the shard is labelled. The label is not the tell: a folder scope with nothing to split by is planned as a single shard labelled `whole drive`, so a connection whose folder scopes were each small enough to stay unsplit persisted a stale plan with no `remainder` shard in it at all. A genuinely whole-drive scope's own shards (`root_item_id=None` is correct there) are unaffected.
- **A named shard re-run applies the same staleness rule.** `POST /api/admin/sharepoint/connections/{id}/extract` with `{"shards": [...]}` reads the persisted plan directly and never consulted the check above, so picking a pre-fix folder remainder by index still launched a whole-drive crawl — the one door left open onto exactly the plans this change discards. It now answers `409 stale_shard_plan`; an ordinary trigger re-plans and the re-run works again. The whole plan is refused rather than the named shards, because indices are positional into it and serving part of a plan would renumber the shards the operator is reading off the run they are retrying.
