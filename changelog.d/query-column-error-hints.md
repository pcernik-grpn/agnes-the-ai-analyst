### Fixed
- **A failed `query` call now names the table to check, not just a bare DuckDB error.** Measured live: `query` is the most-used tool and the most error-prone, with most failures a guessed column name — and two of DuckDB's own error shapes actively worked against recovery. `Binder Error: Table "s" does not have a column named "..."` (also phrased `Values list "s" does not...` for some query shapes) names only the JOIN alias, never the underlying table, so neither the caller nor an agent could tell which relation was meant; `Referenced column "..." not found in FROM clause!` names no relation at all. `POST /api/query` (and every surface that calls it — `agnes query --remote`, the `query` MCP tool) now resolves the alias back to its table from the statement and appends a hint pointing at `schema <table>` (or every table in the query, when there's more than one and no alias to resolve), on top of — never in place of — DuckDB's own message, including its `Candidate bindings:` list when present. A `Catalog Error: Table with name ... does not exist!` for an identifier that looks like a source-system path rather than a registered id (e.g. a Keboola `in.c-<bucket>.<table>` bucket path copied from the semantic layer, DuckDB's own "Did you mean" suggestion notwithstanding) now says so and points at `catalog` to find the real registered id.
