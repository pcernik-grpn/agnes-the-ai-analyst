### Fixed
- **A long Collections file can now be read to the end.** `GET /api/collections/{collection_id}/files/{file_id}/preview` capped its text at 20 000 characters with no way past them, and the chunk join behind it stopped at the same cap — so `collection_file_read` (both MCP servers) and `agnes collections cat` could only ever hand back the first ~20k characters of a document. Observed live: an agent asked to summarise a long slide deck read the first third in full and could reach the rest only by guessing search terms, which is weak on a lexical-only instance. The endpoint now pages: optional `offset` and `limit` query parameters (clamped, never a `422`; `limit` at most 20 000) select one page, and the response adds `offset`, `next_offset` (`null` at the end) and `total_chars`, while `truncated` keeps meaning "this response is not the end of the text". The per-call cap is unchanged — one read still cannot flood a context window; it is a page now, not a wall. `collection_file_read` takes `offset` on both MCP servers, and its docstring says to continue with `offset=next_offset` (and still says a prefix is not the document, and not to loop over a whole collection). `agnes collections cat` follows `next_offset` and prints the whole file by default; `--offset`/`--limit` read a slice (a limited read says so on stderr, naming the offset to continue from) and `--json` emits a single page. For a plain-text upload the 512 KiB read window on disk is unchanged: `total_chars` counts that window and the last page still reports `truncated: true` with no `next_offset` when the file continues past it, so the byte cap is reported rather than hidden by paging. The Library's preview modal sends no parameters and is unaffected.
