### Fixed
- **Triggering a SharePoint extraction right after cancelling a run no longer runs zero files while reporting every shard "done".** Cancelling a run (or the plain Stop control) sets a connection-wide cooperative-stop flag; the ordinary INLINE crawl already cleared a stale flag at its own start, but the auto-parallel planner's SHARDED path (large sites) never called that clear at all. Observed live: a cancel at 17:51:29 left the flag set, an immediate re-trigger planned 989 shards, and every child read the still-set flag and exited instantly — 989/989 shards reported `done`, 0 files walked, 0 failures, looking green while doing nothing; the flag had to be cleared by hand in Postgres before a crawl would run again. The clear now happens exactly once per trigger, before the inline-vs-sharded decision, so both paths are covered — it compares timestamps at microsecond precision (not the second-precision the Stop control used before) so a same-second cancel-then-retrigger orders correctly instead of tying, and the clear itself is an atomic compare-and-delete (a new `clear_stop_requested_if_unchanged` on `source_connections`, both backends) so a stop that commits between the staleness check and the clear is never silently overwritten. A stop requested while the new run is still starting still wins instead of being wiped by that same run's own start-up. The connection-wide flag reaching an in-flight sharded run's children is unchanged and intentional (shard children have no run-scoped stop signal of their own) — but since a cancel closes the top-level run row immediately without waiting for those children to notice, a retrigger now checks the job queue first, by an exact, indexed idempotency-key lookup rather than a fleet-wide `limit`-bounded scan, so a busy fleet's other connections can never hide this one's own child behind it. While any of that connection's shard children are still queued or running, the WHOLE trigger is now refused outright (409 on the selected-shard rerun endpoint, a failed job on the ordinary trigger path) instead of merely leaving the flag in place and enqueuing a fresh plan anyway — a fresh plan's children share the same deterministic idempotency key as the still-live old ones, so enqueuing them would silently alias each "new" child onto a stale one and strand the new run forever, running but never completing. The selected-shard rerun endpoint (`{"shards": [...]}`) gets the same clear-or-refuse, since it enqueues children directly rather than through the ordinary trigger path. Every "unknown" case along the way — a failed liveness check, an unresolvable triggering job — now refuses or preserves the flag rather than guessing it is safe to proceed, so a transient repo error can no longer reproduce the original silent-no-op failure by a different route; only a caller with no job to anchor against at all still clears unconditionally once liveness is confirmed. The connection's own dispatch bookkeeping (`last_run_at`/`last_job_id`) now merges into `config.extraction` through the same one-transaction primitive as the stop flag's own clear, closing a second overwrite window a plain read-then-patch pair still left open.
